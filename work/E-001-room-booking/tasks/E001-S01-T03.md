## Dispatch note
- `src/domain/auth/rules.ts`: pure functions with `@ears` tags. Lockout (5 failures in 15 min), IP delay (from 30 distinct emails, 1 s more each) and block (from 100), password length 12 to 128, 12 h expiry, warning at 5 min before end, role home per role, temp password expiry.
- `src/lib/auth/`: `token.ts` (256-bit CSPRNG token, SHA-256 hex hash, email hash of trimmed lower-cased email), `password.ts` (Argon2id via `@node-rs/argon2`, dummy verify on null), `cookie.ts` (`__Host-session`, HttpOnly, Secure, SameSite=Lax, Path=/), `client-ip.ts` (last `X-Forwarded-For` value, one trusted hop), `return-to.ts` (checked path else role home), `session.ts` (`getSession()` per spec section 3).
- Put the sign-in and password-change flows in `src/lib/auth/sign-in.ts` and `src/lib/auth/change-password.ts` as plain functions that take input, client IP, now and a sleep function, and return a result or throw `AppError`. The `actions.ts` files stay thin: `requirePermission`, parse, call the flow, set or clear the cookie, redirect. T-05 integration tests call the flow functions against the live DB.
- Sign-in order per spec section 3. Only after a verify passes: deactivated (AC-84, `rule-violation` 422), then temp expired. Unknown and wrong both give `unauthenticated` 401 with "Email or password is wrong." Lockout gives `locked` 429 with `Retry-After`.
- Actions return form state for the page (field errors, summary message) instead of throwing to the client. Copy keys from spec section 2.
- `GET /api/health` returns `{ status: "ok" }` and nothing else. Calls `requirePermission(null, 'public')`.
- Log per spec section 5: user id only. Never email, IP, password or token.
- Unit tests here need no DB. Mock the data calls.
